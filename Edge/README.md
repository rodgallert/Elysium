# Edge proxy

One small nginx that is the only thing in the repository publishing a host port. It binds `127.0.0.1:80` and `[::1]:80` (nginx itself listens on 8080 inside the container, as user 101), and routes by `Host` to each stack's entry proxy over the external network `elysium-edge`, which `Edge/docker-compose.yml` creates. The design is `Docs/environments-design.md`, section 3.

```bash
docker compose -f Edge/docker-compose.yml up -d --wait   # start it before any stack
docker compose -f Edge/docker-compose.yml down           # stop it (the stacks keep running, unreachable)
```

## What it does

- **Host allow-list.** Exactly `prince.localhost` (to `prince-prod-proxy:80`) and `prince.dev.localhost` (to `prince-dev-proxy:80`); case, a trailing dot and `:80` are accepted. Anything else (an empty or missing Host, `localhost`, an IP address, another port, a longer name that merely starts with an allowed one) gets `421` with an empty body. Two `Host` headers get `400`. A production name never reaches the dev proxy and the other way round.
- **Malformed requests.** A request nginx can't parse gets the edge's own `400` (with the security headers), never a 5xx and never an upstream: a garbage request line, an invalid method, `GET x`, an invalid percent sequence (`/%zz`), `%00`, a raw space in the path, a path that climbs above `/`, an invalid header line after the `Host` line, two `Host` headers, an over-long line. Only an empty, missing or unknown `Host` is `421`. Residual: an invalid header line sent *before* the `Host` line leaves the Host unread, so it answers `421`. The edge's internal error location `/.edge-400` is not reachable (`404` or `421`).
- **Paths.** Request paths are normalised for every service: percent-encoded characters are decoded once, `//` is merged and `.` and `..` are resolved; then `\ " < > ` | ^` reach the stack percent-encoded (`/a\b` as `/a%5Cb`) and an already encoded `%5C` stays one, so no service depends on its own framework's URL parsing. An encoded slash is decoded too, as the stack's proxy has done since #73: `/api/a%2Fb` reaches the API as `/api/a/b` and `/api/%2F` as `/api/` (spec change of #75-AC6.1; the query string is not touched).
- **Headers.** It sets `Host` (the matched name), `X-Forwarded-For` (one address, see below), `X-Forwarded-Proto: http` and `X-Forwarded-Host`, and removes `X-Real-IP`, `Forwarded`, `X-Forwarded-Prefix`, `X-Forwarded-Port`, `X-Forwarded-Server`, `X-Original-URL` and `X-Rewrite-URL`; whatever the client sent is replaced or dropped. `X-Forwarded-For` holds the address the edge sees, which is Docker's gateway address (for example `172.18.0.1`), not the browser's: that is how Docker publishes a loopback port. No service may use an IP address as identity (platform design, section 20). Every response, errors included, carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` and a report-only CSP (enforcing waits for a UI without inline scripts); a stack's own copies of these headers are dropped, so none is doubled. Cookies pass untouched (host-only).
- **Limits.** Header lines and the request line 8 KiB, body 10 MiB (`413` above), 8 requests with a body at a time (`503` for the 9th), only `Upgrade: websocket` passes (any other `Upgrade`, `h2c` included, is dropped and the request goes out with `Connection: close`), connect timeout 3 s, read and send timeouts 30 s, client header and body timeouts 10 s.
- **Name lookup.** Upstream names are looked up per request through Docker's embedded DNS (`valid=10s`), so the edge starts with no stack running (every known host answers `502`) and finds a stack that starts or is recreated within 10 s (`valid=10s`), with no restart. The test allows 12 s for that window and for the 10 s header and body timeouts, to leave room for a loaded machine.
- **Log.** One JSON line per request on stdout: UTC time, host (the `Host` header as sent, which is what routing reads, not the host of an absolute-form request line), method, path without the query string, status, upstream address, request time. Never the query string, `Authorization`, `Cookie` or a body; a newline or control byte in a path is escaped.
- **Error log.** nginx's own error log is limited to `crit`, because its lines quote the request (query string included). So it no longer logs resolver failures, upstream timeouts, connect errors, or the reason for nginx's own 4xx and 5xx; the access line shows the status and the upstream (`-` when none), nothing more. To find out why a request failed, run a copy of `Edge/nginx.conf` with `error_log /dev/stderr info;` against stub upstreams or a throwaway stack, in a Compose project and on a port of its own (never in place, and never on real traffic: those lines carry query strings).
- **Body cap.** At most 8 requests with a body (`Content-Length` above 0, or any `Transfer-Encoding`) are in flight at once (`limit_conn` on a key that is empty for a request with no body, so a GET is never counted). The 9th gets `503` and reaches no stack; a new upload passes as soon as one finishes. 8 uploads of the maximum 10 MiB are 80 MiB, under the 128 MiB body tmpfs, so it can't fill and nginx never writes the `[crit] pwrite()` line that quotes a request line with its query string (#75-AC3.2).
- **Hardening.** Non-root, `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, `pids_limit: 100`, tmpfs for the pid file (`/tmp`, 16 MiB) and temporary files (`/var/cache/nginx`, 128 MiB), no Docker socket, no network but `elysium-edge`. It never joins a data-store network. The tmpfs sizes, `pids_limit` and the health check's `retries: 3`, `start_period: 5s` and `start_interval: 1s` are PO-confirmed values (2026-11-23).

A stack joins with `networks: elysium-edge: {external: true}` and the alias `<app>-<env>-proxy`, publishing nothing.
