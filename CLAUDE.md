# Elysium — contributor notes

Elysium is an ecosystem of microservices named after the World of Darkness: **shared services** (accounts, ledger, files, ...) that any product can use, and **products** (Prince first) built on them. The design is in `Docs/platform-design.md`; work through `ROADMAP.md` phase by phase and tick off checkboxes as items are completed.

- Stack: .NET 10 (ASP.NET Core, EF Core, ASP.NET Core Identity + OpenIddict, Wolverine, YARP for the gateway), PostgreSQL, RabbitMQ, Redis, Silo (S3-compatible storage), Vue 3 and React frontends, Docker Compose.
- **Sources of truth:** `ROADMAP.md` for what gets built and when; `Docs/platform-design.md` for how the ecosystem fits together; each service's own `CLAUDE.md` and decision log for its specifics. Don't change a rule in code without updating the document that states it, and ask before changing a decided rule.
- **Plain project text:** PR descriptions, issues, comments, reviews and commit messages read like any normal project's: no tool attribution (no "Generated with …" footers, no tool `Co-Authored-By` trailers) and no mentions of how the work is produced. A squash merge copies every commit's trailer into the squash commit, so ticket commits must not carry one either.
- **Breaking changes** (anything that forces a consumer of a service to change — API, message contracts, token claims, irreversible migrations, config keys — and rewrites of code a finished scenario relies on) are flagged in both the issue and the pull request, saying what can break and what consumers need to do or what must be re-tested; the title and commit carry `!` and `BREAKING CHANGE:` (see `Docs/workflow.md`, "Breaking changes").
- **Service isolation:** a service never references another service's projects or reads another service's database. Services talk through versioned HTTP APIs and messages only. Shared services know nothing about the products using them (opaque ids, no product words). `tools/check-boundaries.sh` checks project references.
- **Coding practices:** domain-driven design and SOLID; dependencies point inward (`Domain` has no package or project dependencies); CQRS as described in `Docs/platform-design.md` (separate command and query handlers everywhere, separate read models only where the design says so); published messages go through the outbox; message handlers are idempotent.
- **Zero trust** (`Docs/platform-design.md` §20): every service validates tokens itself (signature, audience, expiry) even behind Keeper; no route skips authentication for being "internal" and no IP address counts as identity (health checks are the only exemption); write everything as production code, as if behind an already-breached VPN.
- **Security:** authentication work follows OWASP ASVS 5.0 Level 2 as written in `Docs/platform-design.md`. Never log passwords, tokens or personal data. Secrets live in untracked `.env` files; `.env.example` holds safe local defaults.
- **Data:** code-first EF Core migrations only, one database per service. Personal data stays in Accounts (Masquerade); products read it through its API.
- **Before opening a PR,** go through the checklist in `Docs/workflow.md` ("Before you open a PR").
- **Branches and reviews** follow `Docs/workflow.md`: trunk-based, every ticket branch squash-merges into `main`, Conventional Commits. Commit only on ticket and hotfix branches, never directly on `main` or a release branch. Phases have no branch: a phase is its epic plus a checkpoint tag on `main`. Every merge needs a passing build, tests and `tools/check-boundaries.sh` (Markdown-only PRs have no build check; they get a read-through and the other checks), and a review by someone other than the PR's author, following `.claude/skills/pr-review/SKILL.md` (docs-only tickets: a read-through instead), and then the PO's approval.
- **Issues and the project board:** every piece of work has a GitHub issue, a branch and a PR, linked both ways; no branch or PR without its issue. At every step (start a ticket or phase, open a PR, merge, phase checkpoint, release, hotfix), follow `.claude/skills/ticket-flow/SKILL.md` so the issue and the "Elysium" project board match the work. Board moves go through `tools/board.sh`.
- **Releases are per service** (`Docs/workflow.md`, "Releases"): a release PR bumps the service's version, its `CHANGELOG.md` and its pin in `docker-compose.prod.yml` (the list of what's in production); CI creates the tag and publishes the image. Every merge into `main` publishes the development images.
- Each service directory has its own `CLAUDE.md` with rules specific to it. Where `Prince/CLAUDE.md` still describes the old single-database model, `Docs/platform-design.md` ("What this overturns") wins for new work.
